## Actual source-to-claim comparisons

### Browser-local notebooks and backup/recovery

- In companion `assets/app.js`, the normal notebook load/save uses the key `research_methods_studio_v1` and `RMSPilot.safeLoad(KEY)`/`RMSPilot.safeSave(KEY, project)`. The latter reads and writes project JSON through browser `localStorage`, and `assets/pilot.js` periodically retains a second **best-effort local recovery snapshot** when a previous saved copy is suitable. If browser storage rejects writes, it returns a failure state and the app shows **“Save problem”**. Those features support a local-first design, without guaranteeing that all browsers will provide durable storage or that an automatic secondary snapshot always exists.
- The application's **Backup JSON** button serializes `RMSPilot.backupEnvelope(project, "full")`. The **Pilot & Recovery Center**, implemented in `assets/pilot-ui.js`, provides full JSON recovery and a separately labelled **privacy-minimized copy**. The latter deliberately omits data and manuscript sections and **cannot** be used as a full recovery backup. Restore reads a user-selected JSON file, checks the envelope's fingerprint and restorable status, asks for confirmation before replacing the project, then attempts to save and reload. The fingerprint is a simple **non-cryptographic stable hash**, not proof of authenticity or encryption. The UI warns that a full export may contain raw data, manuscript text and source notes.
- The `assets/word-export.js` writer serializes structured HTML with Word-specific compatibility markup and `application/msword` MIME type under a **`.doc` file extension**. It is a **Word-compatible document**, not native OOXML `.docx` and not a guaranteed successful import by every word processor. The academic website's precise **“Word-compatible .doc export”** wording is correct.
- A review of `assets/app.js` uncovered a **separate prospective recovery concern**. The **“Download backup and start new”** path invokes a file download and then schedules browser project deletion after **250 ms**, without confirming that the download was actually written to disk. A click to initiate a download is not proof that the user possesses an independently saved backup, particularly if downloads are cancelled or blocked. This is **not** a contradiction in the academic page's more general description of a backup option. It is an **unverified implementation safeguard** requiring separate targeted review, recorded as the next stage rather than silently marked safe.

### Published instructional guidance and the six-field contract

- The companion `assets/public-content-loader.js` explicitly sets **18 stages** and six value fields, `title`, `nav`, `purpose`, `learn_html`, `example_html`, `warning_html`. The loader enforces exact release and stage-record keys, all 18 stage records, phase and stage alignment, absence of duplicate IDs, and safe text/HTML validation. It forms a complete list of patches before modifying any curriculum stage and attempts to restore previous fields if application throws an error. It **does not directly overwrite** the student's project in browser storage.
- The public loader reads only `/content/public` from the configured endpoint with `credentials: "omit"`, `cache: "no-store"` and `referrerPolicy: "no-referrer"`. If the endpoint is missing, the server rejects the request, returns an invalid/incomplete release or exceeds the startup budget, the page uses the locally bundled curriculum. Original code kept **1500 ms** as the startup deadline for the **HTTP response promise**, but cleared the timer immediately after headers arrived. It then awaited `response.json()` without a deadline. A stalled body could therefore postpone the app's first render indefinitely, contradicting the intended bounded fallback even when the HTTP response arrived promptly.
- The **server-side** `backend/cloudflare-workers-ai/content-coordinator-core.mjs` supports a distinct authenticated rollback operation. It validates the target revision, checks the current release ID for concurrency conflicts, constructs a **new chronological rollback release** from an earlier valid revision and writes its revision. The public content loader sees the new current published version when opened. These operations modify published instructional content; they do **not** themselves replace a browser-local student notebook or require a new application version. This supports the existing academic site's cautiously worded rollback claim.

### Operational data and uncertainty

The companion README says v3.0.0 does not enable operational telemetry or research-study data collection, and the public loader visibly sends **no notebook data or administrator credentials** in its content fetch. The app does retain **local** save/runtime event metadata for status and recovery, which is different from collecting participant study records on an external server. Authentication, admin content-publication history and networked Research Chat involve separate services. The academic website correctly attributes the broader data-collection statement to the **documentation** and cautions that the privacy implications depend on implementation and deployment. This review does not independently establish the absence of every possible platform access log, network-side retention or third-party operational telemetry; no broader privacy certification is claimed.

## Correction actually implemented and verified

Three bounded commits were made in the **companion `gmoon-code/research-methods` application**.

1. [Loader fix 8e7f207](https://github.com/gmoon-code/research-methods/commit/8e7f207b8a8c9a217f74fda4fa9a583609d353eb) retains the **same 1500-ms timer** through both HTTP response and JSON body processing. The body is raced against the existing startup deadline; a body stall produces **bundled fallback** and the late body cannot patch curriculum after startup. The timer is cleared on all normal/early-return paths. The change preserves strict release validation and client-only overlay behaviour.
2. [Regression 4cff078](https://github.com/gmoon-code/research-methods/commit/4cff0787db14f258532dea7e9b0b255ce2cf2e78) adds a test for an immediate HTTP 200 response whose `json()` remains pending. The test triggers the deadline, verifies the resulting bundled state and checks that resolving the late body **cannot mutate** the 18 bundled curriculum records.
3. [Automated coverage 19f01bd](https://github.com/gmoon-code/research-methods/commit/19f01bd4e97a4f0069e2f371adb747f0220da558) adds the loader source and its test file to the existing **Content audit regression** workflow path filter and executes the loader test suite in CI, rather than relying only on the preceding research-chat/backend tests.
